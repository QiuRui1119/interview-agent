# Interview Agent 项目总结

更新日期：2026-10-08

本文依据当前源码、构建配置和 Flyway 脚本整理，记录项目技术选型、业务实现、架构亮点和开发过程中暴露的问题。功能状态描述以代码为准，不代表所有外部服务组合都已完成生产环境验收。

## 项目定位

Interview Agent 是一个面向技术面试准备的全栈应用。用户可以上传简历并获取 AI 分析，管理技术知识库并进行 RAG 问答，还可以基于简历和选定知识库创建动态面试、提交多轮回答并生成评估报告。

## 技术选型

| 层次 | 技术 | 用途 |
|---|---|---|
| 后端 | Java 21、Spring Boot 4.1、Gradle | REST API、业务服务、依赖注入和事务 |
| AI | Spring AI 2.0、`LlmProviderRegistry`、`StructuredOutputInvoker` | 多模型配置、Embedding、结构化 LLM 输出 |
| 数据库 | PostgreSQL 17、pgvector、Spring Data JPA | 业务数据和向量检索 |
| 缓存与异步 | Redis 7、Redisson、Redis Stream | 会话缓存和后台分析、向量化、面试生成及评估 |
| 文件 | MinIO/S3 API、Apache Tika | 文件对象存储、简历和知识文档解析 |
| 后端测试 | JUnit 5、Mockito、AssertJ、H2 | 单元及集成测试；pgvector 场景需要真实 PostgreSQL |
| 前端 | React 19、TypeScript 6、Vite 8、`react-router-dom` 7 | 页面、类型、路由和构建 |
| 前端 UI | 自定义 CSS、`lucide-react` | 工作台布局和图标，不使用 Tailwind 或 UI 框架 |

开发依赖可通过根目录 `.env` 和 `docker-compose.dev.yml` 配置 PostgreSQL/pgvector、Redis、MinIO。Gradle `bootRun` 会读取根目录 `.env`；JUnit 测试进程不会自动加载该文件，需要通过运行环境设置测试变量。

## 功能实现

### 简历分析

- `POST /api/resumes/upload` 支持文件校验、内容类型检测、SHA-256 去重、文本解析与清洗、MinIO 上传和数据库保存。
- 分析请求进入 Redis Stream；简历文本随消息发送，避免消费者依赖上传请求现场或重新读取数据库字段。
- 消费者调用结构化 LLM 分析，将评分、摘要、优势和建议保存为分析记录，并更新简历分析状态。
- 提供简历列表、详情、最新分析、删除和重新分析接口。
- 前端简历工作台支持上传、文件列表、异步状态轮询、查看详情、重分析和删除。

### 知识库与向量化

- 支持用户上传文档和内置 Markdown 两类来源；内置资料在应用启动时按稳定 `sourceKey` 和内容 Hash 做幂等同步。
- 用户文件保存到 MinIO；内置文件从 classpath 读取。两类资料通过统一内容加载服务进入相同的清洗、分块和向量化流程。
- 使用 `TokenTextSplitter` 分块，Chunk 元数据包含知识库 ID、来源、分类、版本、Chunk 序号和向量任务 ID；Embedding 按不超过 10 条分批写入。
- 重新向量化先写入临时 job 向量，成功后提升为当前版本并清除旧正式向量；中途失败保留旧版本并清理当前临时向量。
- 用户文档可删除；内置文档通过禁用处理；处理中知识库不能删除或重复提交。
- 管理接口包括列表、详情、上传、重新向量化和删除；前端按来源/状态筛选、搜索、分类、轮询并支持失败重试。

### RAG 问答

- 检索服务负责问题清洗、Embedding、pgvector 相似度检索、知识库范围过滤、阈值过滤、去重和 Top-K。
- 普通问答和 SSE 流式问答共享检索结果，响应提供来源信息，便于判断回答依据。
- Query Rewrite 可结合历史消息改写追问，并合并原问题与改写问题的结果；功能有独立开关、长度限制、超时和统计。
- 问答 Prompt 位于 `resources/prompts/`，要求只依据资料回答、资料不足时拒答，并把检索文本作为数据而不是指令处理。
- 前端提供知识库选择、流式回答、Markdown 渲染、引用来源和中断后重新提问。
- 仓库包含 33 条检索评估问题和 16 条回答问题。现有环境门控的评测代码主要执行检索指标（Hit@K、Recall@K、MRR、拒答及来源准确率）和 Query Rewrite 对比；回答问题集尚未形成完整自动评分流程。

### 动态面试

- 创建前检查简历分析完成，并校验所选知识库启用且向量化完成；当前配置固定为 5 个 Topic、每 Topic 最多 1 次追问、最多 10 轮。
- Topic 和 Turn 使用独立数据库实体。Topic 保存目标、参考答案、评分点、状态、追问次数及 Evidence 快照 JSON；Turn 保存问题、答案、父子关系、决策和幂等 `requestId`。
- 状态精简为 Session：`CREATED / IN_PROGRESS / COMPLETED / ABORTED`；生成和评估分别使用 `PENDING / PROCESSING / COMPLETED / FAILED` 任务状态。
- 创建会话后异步规划 Topic、检索知识片段并生成主问题和备用追问。
- 答案提交由 `InterviewAnswerService` 编排：事务内保存回答和 `DECIDING`，事务外调用 LLM，事务内保存决策并创建下一 Turn。重复 `requestId` 返回原结果；刷新页面时 `/resume` 可恢复未完成决策。
- Redis 保存会话热缓存，数据库是最终事实来源；缓存丢失后通过会话服务从 PostgreSQL 重建。缓存更新通过事务提交事件触发。
- 面试结束后通过独立评估 Stream 生成结构化报告并存回 Session JSON；综合分数、评估时间单独存列。评估只使用 Topic 中保存的出题时 Evidence 快照，不重新查询当前知识库。
- 提供会话历史、恢复、报告状态、报告内容和评估重试接口。前端有创建页、生成等待页、动态答题页、历史列表和报告页。

### Redis Stream 重试

- 四类后台任务共用 `AbstractStreamProducer`/`AbstractStreamConsumer`：简历分析、知识库向量化、面试生成和面试评估。
- 新消息携带 `retryCount=0`；业务失败后立即重投到同一 Stream，计数递增至 1、2、3；计数为 3 的消息再次失败时才调用对应业务的最终失败处理。
- 重投写入成功后 ACK 原消息；重投写入失败时不 ACK 原消息，让已有 Pending reclaim 机制恢复。
- 当前是立即重试，Pending reclaim 空闲阈值为 5 分钟。尚未实现指数退避、死信 Stream、通用幂等任务 ID 或队列积压/Pending 指标。

## 架构亮点

- 外部 LLM、Embedding、文件存储调用与数据库短事务分离，避免长时间占用数据库事务。
- Redis Stream 消息尽量自包含或只传稳定业务 ID；生成和评估状态落在业务表中，便于页面恢复和排查。
- 面试答案幂等使用数据库唯一约束、Turn 当前状态和 `requestId`；Topic/Turn 分表保留细粒度更新和崩溃恢复能力。
- 知识库重新向量化通过临时版本提升，失败时保留旧可用向量。
- 面试 Evidence 快照冻结了出题时的资料版本，使后续知识库更新不会悄悄改变同一场面试的评估依据。
- 前端轮询使用递归 `setTimeout`、请求序号或 `AbortController`，并在页面隐藏时暂停；避免固定 `setInterval` 导致请求重叠。

## 开发中遇到的问题

### 数据库结构与迁移

- 开发中出现过实体字段与数据库字段不一致，项目使用 Flyway 和 `ddl-auto: validate`；应以迁移历史决定新增迁移还是修正未执行迁移，不能改写已执行版本。
- 当前 Flyway 脚本已合并为单一 `V1__init_schema.sql`，用于空库初始化最终结构。
- 已有数据库仍保留旧版本 Flyway 历史；重建前不要直接让应用使用合并后的迁移启动，否则 Flyway 可能因历史版本脚本缺失而校验失败。

### 环境变量和集成测试

- `.env` 是 Gradle `bootRun` 的输入，但测试由 Gradle Test Worker 启动，不会天然继承 Gradle 脚本解析 `.env` 的逻辑。
- pgvector 无法用 H2 验证；向量集成测试和 RAG 评测需要显式配置 PostgreSQL、Embedding 服务及对应环境变量，并由环境变量开启。
- Redis、PostgreSQL、MinIO、Embedding/LLM 服务任一未启动或配置错误，都会造成端到端流程无法完成；单元测试通过不代表外部服务链路已验收。

### 异步状态和恢复

- 初期页面曾以“分析结果是否存在”判断是否继续轮询；后来改为显式任务状态，避免失败任务永远等待。
- 面试曾把 Topic/Turn 状态写入 Redis 作为唯一恢复来源；目前采用数据库最终事实来源、Redis 热缓存和缺失时重建。
- 评估报告最初只有后台保存，没有查询协议；现在报告接口统一返回任务状态、错误和报告，前端可以只轮询一个接口。
- Redis Stream 目前有最多 3 次立即重投，但不是延迟退避，也没有 DLQ 和通用消息幂等。跨进程 ACK 失败后可能重复消费，因此仍需检查每个业务处理器的状态幂等。

### 面试流程边界

- 动态面试使用 Topic 与 Turn 实体，而不是把所有问题塞进 Session JSON，因为需要逐轮答案持久化、幂等、父问题关联和 `DECIDING` 恢复。
- Session 已简化为四种状态，生成/评估分别用异步任务状态表达；合并后的初始化 SQL 直接建立最终状态约束。
- 当前没有提前结束面试的 API，也没有生成失败后的重新生成接口。答案判断 Prompt 使用当前问题、回答、Topic 目标、评分点和参考答案；最近对话与 Evidence 还没有进入该决策 Prompt。

### 前端验收

- 前端经历过从手写路径判断切换到 `react-router-dom`、从 Session ID 手工输入切换到创建配置页，以及增加报告和历史记录页的过程。
- 目前有 Oxlint 和 TypeScript/Vite 生产构建，但没有 Playwright/Cypress 自动化流程；移动端布局主要由 CSS 断点和构建检查验证，尚未形成截图回归。

## 测试与运行

后端常规测试：

```powershell
.\gradlew.bat :app:test --no-daemon
```

前端检查：

```powershell
cd frontend
npm run lint
npm run build
```

开发依赖：

```powershell
docker compose -f docker-compose.dev.yml up -d
```

向量集成测试及 RAG 检索评测默认受环境变量控制，运行前应检查测试类说明并设置相应变量。API Key 和数据库凭证只从本地环境变量读取，不应复制进此文档或提交到 Git。
